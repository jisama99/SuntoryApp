# Revue et fusion d'un lot (D191)

Version du 23/10/2026. À coller dans une **nouvelle** session Claude Code (jamais celle qui a écrit le lot), dans le dépôt `08_PLATEFORME_SUNTORY_V3`, après le message de lancement `29_MESSAGES_DE_LANCEMENT.md` section « Message de revue ». Paramètres : `<CODE>` (lot), `<BRANCHE>` (branche de session du lot, indiquée dans le récapitulatif de fin de lot).

RÔLE
Tu es relecteur indépendant. Tu n'as pas écrit ce lot. Tu ne t'auto-évalues pas : tu vérifies par preuve. Une hypothèse n'est pas une décision. Données fictives uniquement ; Supabase, Vercel et toute requête externe interdits ; aucun fichier de données réelles lu.

AUTORISATION (D191) : tu peux créer la branche `revue/<CODE>` depuis `<BRANCHE>`, y commiter tes corrections, puis, aux conditions de l'étape 9 seulement, fusionner dans `main` et pousser `main`. Jamais de poussée forcée, jamais de pull request sans demande, jamais d'inscription au registre d'une décision non validée par T. SOEFOU.

ÉTAPES
1. Mise en place : `git fetch origin` ; vérifie que `origin/<BRANCHE>` existe et qu'elle contient `origin/main` (sinon, signale-le et fusionne `origin/main` dans `revue/<CODE>` en traitant les conflits sans perdre de contenu) ; crée `revue/<CODE>`.
2. Lectures : `docs/PROMPTS` du lot (critères), `docs/COMPTE_RENDU_<CODE>.md`, `docs/DECISIONS.md`, règles communes (10, 12 à 16), `git diff origin/main...origin/<BRANCHE> --stat` puis le diff détaillé des fichiers de logique, de données et de tests.
3. Audit (règle 17, D192 : sous-agents au modèle le plus économique suffisant pour les tâches mécaniques, par exemple recherches, listes de fichiers, lancement et résumé des contrôles ; le modèle principal garde la sécurité, les droits, la vie privée, les arbitrages et le verdict) : lis et applique les grilles de `agents-projet/` (revue de code, accessibilité, i18n, sécurité du code généré, minimum de modification ; vie privée et identité et accès pour les lots qui touchent aux comptes, aux profils ou aux données personnelles). Classe les constats : bloquant, important, mineur. Cherche en particulier : audience par défaut refusée contournée, code de zone affiché sans `ZoneLabel`, style ou texte en dur, chaîne non traduite, référence interne dans un texte affiché (D182), date saisie sans sélecteur (règle 12), jours de semaine hors `WeekdayPicker` (règle 13), requête externe, donnée ou fichier interdit, test qui ne prouve rien.
4. Contrôles, sortie reportée dans le rapport : `npm ci` si besoin, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, `npm run test:e2e` (si Chromium manque de bibliothèques, utilise le Chromium préinstallé `/opt/pw-browsers` avec une configuration Playwright locale non commitée ; arrête les serveurs `next` entre deux séries en visant leur PID, pas par motif). Un contrôle non exécuté est écrit « non exécuté » avec la raison, jamais « passé ». Le contrôle C3 est hors session (fichier local `.denylist.local`) : écris-le comme tel.
5. Règles communes : vérifie une à une les règles 10, 12, 13, 14 (adresses, états chargement, vide et erreur, focus, lien d'évitement, 390 px, seuils 2 s et 100 ms), 15 (anglais, glossaire) et 16 (jetons, transitions, cibles de 44 px), avec la commande ou le test qui le prouve.
6. Captures : ouvre et regarde **chaque** capture du lot (`docs/captures/<CODE>/`), en notant lesquelles tu as vues ; signale les défauts visuels (débordement, contraste, texte tronqué, mélange de langues, ancien titre).
7. Corrections : corrige sur `revue/<CODE>` les défauts mineurs et importants dans le périmètre du lot, un commit par correction, test d'abord quand c'est du comportement ; ne refais pas le lot ; un bloquant que tu ne peux pas corriger sans refaire le lot devient un « non fusionnable ».
8. Rapport `docs/REVUE_<CODE>.md` : conformité critère par critère du prompt du lot (preuve), constats et corrections, contrôles et sorties, captures vues et non vues, écarts restants, verdict **fusionnable** ou **non fusionnable** avec les raisons. Puis soumets à T. SOEFOU, par questionnaire (une question par décision, 2 à 4 options, ta recommandation en premier, 4 questions au plus par appel), les propositions de registre du compte rendu et les hypothèses à trancher. Attends les réponses.
9. Fusion, si et seulement si : verdict fusionnable, tous les contrôles exécutés et verts, aucun bloquant, validation de T. SOEFOU reçue dans cette session. Alors : inscris dans `docs/DECISIONS.md` les décisions validées avec les numéros proposés (les refusées sont notées « refusée »), mets le glossaire à jour si nécessaire, commit ; `git checkout main` ; `git pull --ff-only origin main` ; `git merge --no-ff revue/<CODE>` ; relance `npm run typecheck` et `npm test` sur le résultat ; `git push origin main`. Si le push est refusé (protection de branche ou droits), arrête-toi, ne cherche aucun contournement, et indique la commande à lancer par T. SOEFOU. Sinon, ne fusionne pas : liste ce qui manque.
10. Fin : récapitule en dix lignes maximum : verdict, SHA de la fusion, contrôles, décisions inscrites, constats restants, **copie miroir à synchroniser** (le dossier `07_DEV_CLAUDE_CODE` est hors dépôt, à faire par T. SOEFOU ou par son assistant), message du lot suivant à lancer. N'enchaîne pas sur le lot suivant.
